# Instructions for AI Coding Agents

## Project Objective

This repository implements a reproducible experiment pipeline for a feasibility-aware predict-then-optimize matheuristic on the Multi-item Capacitated Lot-Sizing Problem (MCLSP). The active workflow generates instances, solves exact and relaxed MILP models, trains classifiers to predict binary setup decisions, and evaluates restricted MILPs using ML-based fixing and feasibility repair.

Prioritize correctness, reproducibility, and consistency with the existing experiment pipeline.

## Repository Structure

- `config.py`: central configuration. Treat it as the source of truth for parameters, feature sets, model lists, and paths.
- `01_generate_instances.py`: phase 1 instance generation.
- `02_solve_optimal.py`: phase 2 exact and relaxed optimization.
- `03_train_model.py`: phase 3 classifier training and artifact persistence.
- `04_evaluate_matheuristic.py`: phase 4 matheuristic evaluation.
- `functions.py`: shared optimization, ML, repair, plotting, and experimental helper functions.
- `documents/`: research documents and PDF text extraction script.
- `results_exp0/`: generated experiment data, models, scalers, and hyperparameter outputs.

## Coding Conventions

- Follow the existing procedural Python style unless performing an explicit refactor.
- Keep experiment settings in `config.py`; do not duplicate constants in phase scripts.
- Preserve Spanish column names and existing artifact naming conventions.
- Use pandas DataFrames for data tables, as the current pipeline does.
- Keep Gurobi model variables and notation consistent with the current code:
  - `x`: production.
  - `s`: inventory.
  - `y`: binary setup.
- Use instance-level splits for ML validation and testing.
- Avoid changing generated data files unless the task explicitly requires regenerating experiment outputs.

## How to Run

Run scripts from the repository root:

```bash
python3 01_generate_instances.py
python3 02_solve_optimal.py
python3 03_train_model.py
python3 04_evaluate_matheuristic.py
```

The optimization phases require Gurobi and a valid license.

## How to Run Tests

No automated test suite exists in the current repository.

Recommended checks after changes:

- Import check:

```bash
python3 -c "import config; import functions"
```

- For pipeline changes, run a reduced-size configuration in `config.py` before attempting the full experiment.
- Confirm generated Excel columns match downstream expectations.
- If modifying Gurobi logic, test on one small instance first.

Do not claim full validation unless the relevant numbered phases were actually run.

## How to Add New Features

1. Identify which pipeline phase owns the new behavior.
2. Add configuration knobs to `config.py` when the behavior should be reproducible.
3. Keep file naming consistent with the existing `{artifact}_{split}_n{items}_p{periods}_c{c}_f{f}_s{seed}` convention.
4. Add shared helpers to `functions.py` only if multiple scripts need them.
5. Preserve existing output schemas unless downstream scripts are updated together.
6. Document new feature sets, models, or outputs in `README.md` and `context.md`.

## Constraints and Best Practices

- Do not invent experiment results. Only document or report values produced by code or existing artifacts.
- Do not silently alter `TRAIN_PARAMS`, `TEST_PARAMS`, `ML_CONFIG`, or `EVALUATION_CONFIG`; such changes affect all downstream filenames and results.
- Avoid broad refactors in `functions.py` unless specifically requested.
- Keep active pipeline code separate from legacy experimental variants where possible.
- Be careful with Gurobi parameters: the code uses both `TimeLimit` and `WorkLimit` in different functions.
- Be careful with callback-derived metrics and `gurobi_optimization.log`; multiple functions can overwrite or parse the same log file.
- Pickled models and scalers must be saved and loaded as pairs using matching feature columns and naming.
- Do not split rows from the same `Instancia` across train/test folds.
- Treat generated Excel and pickle artifacts as experiment outputs, not source code.

## Critical Files

Modify these only with clear justification:

- `config.py`: changes alter experiment identity, file names, data size, solver limits, and feature definitions.
- `functions.py`: contains core MILP formulations, repair logic, and ML training wrappers.
- `results_exp0/data/optimal/*.xlsx`: used as ground truth and relaxation-feature input.
- `results_exp0/models/*.pkl` and `results_exp0/scalers/*.pkl`: consumed by evaluation.
- `gurobi_optimization.log`: generated by Gurobi; do not rely on it as stable source data unless the relevant function explicitly parses it.

## Architecture Consistency Rules

- Preserve the four-phase execution model unless the task is to redesign the pipeline.
- Keep downstream phases compatible with upstream artifact names.
- Keep feature set names aligned with `ML_CONFIG`:
  - `A`: original cost/demand/setup features.
  - `B`: relaxed solution features.
  - `B_hat`: root-node relaxation features.
- If adding another model, implement save/load behavior compatible with `03_train_model.py` and `04_evaluate_matheuristic.py`.
- If adding another problem class, isolate it clearly instead of mixing its formulation into the current MCLSP functions without naming boundaries.
- Update documentation whenever behavior, required dependencies, or artifact schemas change.
