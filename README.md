# MLforCO

MLforCO is a Python experiment pipeline for studying a feasibility-aware predict-then-optimize matheuristic for the Multi-item Capacitated Lot-Sizing Problem (MCLSP). The code generates synthetic MCLSP instances, solves exact and relaxed MILP models with Gurobi, trains classical machine learning classifiers to predict binary setup decisions, and evaluates restricted MILPs that fix binary variables from ML predictions.

The current implementation is organized as "Experiment 0", with configuration and outputs stored under `results_exp0`.

## System Purpose

The project supports computational experiments for repeated operational 0-1 MILPs, specifically MCLSP instances. It aims to reduce optimization time by learning binary production/setup decisions from solved instances, then using those predictions to restrict later MILP solves while preserving or recovering feasibility.

The domain context is documented in `documents/MachineLearning_for_CombinatorialOptimizacion.txt` and `documents/Roadmap_Catalina.txt`. The roadmap frames the work as a small-data, feasibility-aware matheuristic rather than a broad general solution for all combinatorial optimization problems.

## Configuration

All active experiment configuration is in `config.py`:

- `TRAIN_PARAMS`: training instance generation and solver settings.
- `TEST_PARAMS`: test instance generation and solver settings.
- `COST_RANGES`: documented generation ranges used by `crear_base_datos`.
- `EXPERIMENT_ID`: currently `exp0`; used to build output paths.
- `PATHS`: data, model, scaler, parameter, and results directories.
- `ML_CONFIG`: active model list, feature sets, and feature combinations.
- `EVALUATION_CONFIG`: prediction threshold, fixing strategy, and evaluation time limit.

No environment variables were found in the source code.

## Execution and Usage

Run the numbered scripts from the repository root in order:

```bash
python3 01_generate_instances.py
python3 02_solve_optimal.py
python3 03_train_model.py
python3 04_evaluate_matheuristic.py
```

The pipeline assumes file names generated from `config.py` parameters. If you change instance counts, item counts, horizons, capacity factors, setup factors, or seeds, downstream scripts will look for matching filenames.

### Phase Outputs

1. `01_generate_instances.py`
   - Writes instance tables to `results_exp0/data/train` and `results_exp0/data/test`.
   - Writes metadata with period and item counts.

2. `02_solve_optimal.py`
   - Loads generated instances.
   - Solves exact MCLSP models, binary relaxations, and root-node relaxations.
   - Writes optimal variables and metrics to `results_exp0/data/optimal`.

3. `03_train_model.py`
   - Loads training optimal variables.
   - Creates target column `binaria` from rounded `y_pre`.
   - Trains configured classifiers over configured feature combinations.
   - Writes pickled models, scalers, hyperparameter records, and consolidated training metrics.

4. `04_evaluate_matheuristic.py`
   - Loads test optimal variables and metrics.
   - Loads trained model/scaler pairs.
   - Predicts setup probabilities, fixes binary variables by threshold, and solves restricted MILPs.
   - Writes final evaluation metrics under `PATHS['results']`.

## Data Columns

Generated instance files contain:

- `Instancia`
- `Periodo`
- `Item`
- `Costo_Produccion`
- `Costo_Inventario`
- `Demanda`
- `Costo_Setup`
- `Capacidad`

Optimal variable files add:

- `x`, `s`, `y_pre`, `y`
- `x_relaxed`, `s_relaxed`, `y_relaxed`
- `x_relaxed_rootnode`, `s_relaxed_rootnode`, `y_relaxed_rootnode`
- `mu`

Metric files include objective values, gaps, solve/work time, node counts, relaxation metrics, and feature generation time.

## Developer Guide

- Keep `config.py` as the source of truth for experiment parameters and paths.
- Preserve the numbered pipeline order unless refactoring the workflow deliberately.
- Prefer adding new reusable behavior to `functions.py` only when it is shared across phases. Otherwise keep phase-specific logic in the relevant numbered script.
- Maintain the existing filename convention: `{artifact}_{split}_n{items}_p{periods}_c{c}_f{f}_s{seed}`.
- Split train/test data by instance, not by row, when adding model evaluation logic.
- Be careful with `functions.py`: it contains active functions plus legacy alternatives. Verify whether a function is called by the numbered scripts before modifying it.
- Gurobi-heavy phases can be expensive. Use small configurations for smoke tests when changing flow or file naming.

## Known Risks and Technical Debt

- No dependency manifest is present.
- No automated tests are present.
- `functions.py` is large and mixes active pipeline functions with older variants, plotting utilities, and experimental code.
- Some functions reference hardcoded paths from earlier experiments.
- Several routines depend on `gurobi_optimization.log` and Gurobi callback behavior.
- Training invokes optimization-based validation via `vars_a_levantar_train`, so it is much more expensive than ordinary classifier training.
- The active pipeline assumes all upstream artifacts exist and does not provide robust missing-file handling.
